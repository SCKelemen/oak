# IO: completion-driven storage and network ports

Status: increments 2, 3 and 5 of §8 are implemented — `iosim`
(`stdlib/iosim.oak`) and the portable `ionative` backend
(`stdlib/ionative.oak` over `stdlib/native/oak_io_host.c`) — with the port
surface below: the file operations, directory sync as op 7, and the
directory and metadata operations 8–13 (exclusive create, truncate,
readdir, rename, stat, unlink) the storage engine's recovery rule needs;
selection by `replace io => iosim | ionative`; and `Oak.IoPort`
(`spec/lean/Oak/IoPort.lean`) proving the §3 contract's link, durability,
read-after-write, and directory clauses over the model. `io_uring`
(increment 4) is not. The document fixes the
interface both realizations must satisfy — the simulated one, built from the
testing module's device, crash and scheduling pieces (`110-testing.md`), and
the native one, built from extern bindings — so that a program has one text
and the deterministic simulation and the operating system see the same
calls. It answers issue #106, the largest gap the database evaluation named.

## 1. Position

Correctness lives above physical IO. A program compiles against a *port*:
an Oak module whose declarations are the operations below. Two modules
realize the port:

- `io/sim` — pure Oak in the testing module: files over `SimDisk`,
  completions ordered and delayed by the tape through `SimSched`, faults
  from the device's ledger, crashes through `SimProcess`. Every operation
  is a trace event, so a failing history explains itself.
- `io/native` — extern bindings (`92-ffi.md` §2.3), each declaring
  `effects { Os.Syscall }` and, where it waits, `Thread.Block`. Linux first;
  a portable `pread`/`pwrite`/`fsync` backend, then `io_uring` behind the
  same rings.

Selection is static and per build: the root manifest's `replace` directive
(`83-modules.md` §4) maps the port's module path to one realization. Nothing
in the program text changes between a simulation build and a native one.
Two existing rules then do the rest: a package with `Sim` tests rejects
undeclared externs, so the native realization cannot be linked into a
simulation by mistake; and a hot path that declares `forbids { Os.Syscall }`
proves, over the specialized call graph, that it never reaches the
operating system (`60-effects-allocation.md` §2).

## 2. Shape: caller-owned completion rings

The port is io_uring-shaped because that is the shape a storage engine
wants (dbs RFC 0002 §12: batched submissions and completions, registered
files and buffers, linked write-then-fsync, bounded prefetch), and because
a synchronous call is the degenerate case of it. Everything is caller-owned
and bounded; `Memory.Allocate` never appears.

```oak
IoFile: type = struct { slot: u32 }                       // registered file, bounded table
IoBuffer: type = struct { base: u32, len: u32 }           // window into the registered region
IoRequest: type = struct {
  op: u32,        // 1 open, 2 close, 3 pread, 4 pwrite, 5 fsync, 6 fdatasync, 7 fsyncdir,
                  // 8 create, 9 truncate, 10 readdir, 11 rename, 12 stat, 13 unlink (16.. reserved: accept, recv, send)
  file: u32,      // IoFile.slot (open/create: the slot to fill)
  offset: u64,    // byte offset for pread/pwrite; the new size for truncate; the split of a two-part window for rename/readdir
  buf: IoBuffer,  // pread/pwrite window; open/create/unlink/fsyncdir: the path bytes; rename/readdir/stat: see below
  tag: u64,       // returned unchanged in the completion
  link: Bool      // this request must complete before the next submitted one starts
}
IoCompletion: type = struct { tag: u64, result: u32, error: u32 } // error 0 = ok, result = bytes
IoRing: type = struct { submitted: u32, completed: u32, files: u32, pending: u32, region_len: u32 }

io_attach: (data: []u8, faults: u32): ()                  // sim: the tape and fault mask; native: ignored
io_open_region: (ring: [*]IoRing, region: [*]u8, files: u32): ()
io_request: (op: u32, file: u32, offset: u64, base: u32, len: u32, tag: u64, link: Bool): IoRequest
io_buffer: (base: u32, len: u32): IoBuffer
io_submit: (ring: [*]IoRing, requests: [*]IoRequest, request: IoRequest): Bool   // false when full
io_wait: (ring: [*]IoRing, requests: [*]IoRequest, completions: [*]IoCompletion, region: [*]u8, at_least: u32): u32
io_poll: (ring: [*]IoRing, requests: [*]IoRequest, completions: [*]IoCompletion, region: [*]u8): u32
```

- **Region.** One caller-owned byte region is registered with the ring;
  every buffer is a window `(base, len)` into it. This is the borrow rule
  made useful: views cannot be stored in requests (`50-borrowing.md`), so
  requests carry indexes into a region the caller passes to each call, and
  the native realization registers that region once (fixed buffers).
- **Files.** A bounded table of slots; `open` fills a slot, `close` frees
  it. The native realization registers the table's descriptors once.
- **Rings.** Submission and completion storage are caller-owned arrays of
  declared capacity; `io_submit` returns false when full, like
  `sim_schedule`. `io_wait` blocks until at least `at_least` completions
  are available (`Thread.Block`); `io_poll` never blocks.
- **Links.** A request with `link` set must complete before the next
  request submitted after it starts; a failure cancels the rest of the
  chain (their completions carry `Canceled`). `pwrite` linked to `fsync`
  is the durability idiom.
- **Errors.** A closed set carried in `IoCompletion.error`: `NotFound`,
  `Exists`, `Access`, `Busy`, `NoSpace`, `Invalid`, `Closed`, `TooLarge`,
  `Interrupted`, `Canceled`, `IoFailed`. The native realization maps errno
  onto it and records the raw code in the trace; no code becomes semantics
  the port did not name.

Synchronous helpers (`io_pread_sync`, `io_pwrite_sync`, `io_fsync_sync`)
are ordinary Oak over submit and wait, for programs that want the simple
shape; they inherit `Thread.Block` and `Os.Syscall` through the call graph.

- **Directory sync.** `fsyncdir` (op 7) takes the directory's path bytes in
  the request's window and makes the directory's entries durable: a log
  whose recovery depends on a renamed or newly created file needs it after
  the file's own fsync.
- **Paths.** A path is a window of one to 32 bytes whose last byte is NUL
  (checked before any storage is touched, and again by the native shim
  before the bytes reach the kernel). `open` (op 1) opens the named file,
  creating it when absent; `create` (op 8) creates it and completes
  `Exists` when it is present — the atomic if-absent creation the storage
  engine's port requires. `unlink` (op 13) removes the name; handles open
  on the file keep working until they close.
- **Two-part windows.** `rename` (op 11) and `readdir` (op 10) carry two
  things in one window, split at `offset`: for rename the old name then
  the new one (an existing file under the new name is replaced, as POSIX
  does); for readdir the directory's path then the output, into which the
  entries other than `.` and `..` are written NUL-terminated, one after
  another, the result being the bytes written — `TooLarge`, contents
  unspecified, when they do not fit. The port promises no order; the
  program sorts.
- **Size.** `stat` (op 12) completes with the file's size as its result
  and, when the window holds eight bytes, writes the size into it as a
  little-endian `u64`. `truncate` (op 9) makes `offset` the file's size:
  shrinking hides the tail, growing zero-fills it, as the file system
  does; a write past the end leaves a hole of zeros.
- **Codes.** Op and error codes are exposed as functions
  (`io_op_pwrite()`, `io_err_closed()`), and `io_request`/`io_buffer`
  build requests through the port's own names.
- **Completion storage.** A call to `io_wait` or `io_poll` completes into
  the caller's completion storage from index 0 and returns the count; the
  storage must hold every pending request (asserted), and the caller
  consumes it before the next call. Executed requests leave the
  submission storage in submission order.
- **Attachment.** `io_attach(data, faults)` binds the simulated realization
  to a run's choice tape and fault mask; the native realization ignores
  both, so the line is the same in every build (§7, question 3).

## 3. Contract both realizations satisfy

- **Completion order.** Completions are unordered except along a link
  chain. A program that needs order links or waits.
- **Reads see writes.** Within one process, a `pread` submitted after a
  `pwrite`'s completion on the same file and range observes it, fsync or
  not.
- **Durability.** A completed `fsync` (or `fdatasync`) means every `pwrite`
  completed on that file before the fsync was submitted — and the file's
  size — is durable across a crash, as far as the device is honest. The
  simulated device's lost-fsync fault exists precisely to test what a
  program does when it is not; the contract is stated against an honest
  device, and the ledger says when the device lied.
- **Directory durability.** A file's existence and name are durable only
  after a completed `fsyncdir` on its directory: a `create`, `rename` or
  `unlink` (and the creation `open` performs) that no `fsyncdir` covers may
  be undone by a crash, whatever `fsync` said about the file's bytes. This
  is POSIX's rule and the storage engine's own discipline (`SyncDir` after
  `Create`); the simulated realization enforces it literally, and its first
  WAL scenario was corrected by it. `Oak.IoPort.syncdir_makes_durable` and
  `crash_forgets_unsynced` state it.
- **Crash.** Writes not covered by a completed fsync may vanish, in whole
  or as a prefix at block granularity (the torn write). A crash closes
  every file; restart reopens. The simulated realization is `sim_disk_crash`
  over the file table; the native one is the machine.
- **No hidden work.** No realization allocates, spawns, or retries on its
  own. A retry is a program decision with a new tag.

## 4. Simulated realization

Files are byte ranges over `SimDisk` blocks — one device of 1024 blocks of
64 bytes holding up to 16 named files of 4 KiB in one flat directory of
32-byte names; `pwrite` packs bytes into words and may tear at block
boundaries exactly as the device does; `fsync` persists a file's bytes and
size; faults come from the tape through the device's mask. The directory
keeps a visible and a durable copy of every entry's name and existence:
`fsyncdir` copies visible to durable, a crash reverts visible to durable,
exactly as the device does for blocks. `io_wait` and `io_poll` pick the
next completion chain through `SimSched` over the pending chains, so the
order is tape-chosen but the oldest pending chain is served within the
scheduler's fairness bound (`iosim_max_wait`); `io_poll` may stop early by
a tape choice. The realization owns a `SimProcess`: `iosim_crash_at(now)`
is the scenario's crash event (files close, unsynced bytes, sizes and
directory changes vanish, the process is down), `iosim_restart` the
restart (an epoch advances, `iosim_restarts`), and a submit or wait while
down is a scenario error and asserts — the rule of `110-testing.md`
"Crashes and scheduling". Every submit and completion is a trace event
with the request's tag, so the runner's replay report names the operation
that failed; `iosim_exists_now`/`iosim_exists_durably` answer a
scenario's directory questions.

## 5. Native realization

Linux first. Increment one is the portable backend — `open`, exclusive
`create`, `close`, `pread`, `pwrite`, `fsync`, `fdatasync`, directory
`fsync`, `ftruncate`, `readdir`, `rename`, `fstat`, `unlink` as extern
bindings with `effects { Os.Syscall }` (`stdlib/native/oak_io_host.c`, one
POSIX call each — readdir one directory walk — no allocation, every path
re-checked to end in NUL before it is a C string), `io_wait` executing
pending requests in order (so links are trivially honored) and declaring
`Thread.Block`. Increment
two is `io_uring` behind the same rings: registered files and the
registered region as fixed buffers, `IOSQE_IO_LINK` for links, batched
submission, `Direct IO` as an open flag for engines that own their cache.
macOS and other targets use the portable backend. The binding is the
trust boundary (`92-ffi.md` §2.3); the realization module carries an
audit list of its bindings.

## 6. What this is not

Not an asynchronous runtime: there are no coroutines or callbacks in the
port; resumption is the program's loop over completions (dbs RFC 0002 §13
keeps coroutines above IO). Not a socket API yet: the ring shape reserves
`accept`, `recv`, `send` as operations over the same region and tags, and
the simulated realization would route them through the event queue; that
is the second design. Not a file system: paths are opaque bytes handed to
`open`.

## 7. Questions for the owner before implementation

1. Module path and selection: is `replace io => ./io_sim` the right way to
   pick a realization, or should the manifest gain a `realize` directive so
   the choice is named for what it is? **Answered:** `replace io => iosim`
   (or `ionative`) — a replace whose target is a standard library package
   name rather than a directory, needing no `require`; the loader loads
   that source under the port's path so its names qualify as `io.`
   (`83-modules.md` §4). No new directive.
2. One registered region or several: one keeps buffers as `(base, len)`
   indexes and matches io_uring's fixed buffers; several would need a
   region index in `IoBuffer`.
3. Whether the port should expose `open` at all, or whether the file table
   is filled at startup by the program's initialization phase (which
   `steady` in `oak.mod` would then keep the steady state away from).
   **Answered for now:** `open` is an op and the caller names the slot; the
   simulated realization keys files by slot (the path is opaque) so a
   restart reopens the same bytes.
4. Whether `fsync` should be split (`fdatasync` only) for the first slice
   of the database engine.
