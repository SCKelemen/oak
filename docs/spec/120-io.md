# IO: completion-driven storage and network ports

Status: design. Nothing in this document is implemented. It fixes the
interface both realizations must satisfy — the simulated one, built from the
testing module's device, crash and scheduling pieces (`110-testing.md`), and
the native one, built from extern bindings — so that a program has one text
and the deterministic simulation and the operating system see the same
calls. It answers issue #106, the largest gap the database evaluation named.

## 1. Position

Correctness lives above physical IO. A program compiles against a *port*:
an Oak module whose declarations are the operations below. Two modules
realize the port:

- `io/sim` — pure Oak in the testing module: files over `SimDisk`,
  completions ordered and delayed by the tape through `SimSched`, faults
  from the device's ledger, crashes through `SimProcess`. Every operation
  is a trace event, so a failing history explains itself.
- `io/native` — extern bindings (`92-ffi.md` §2.3), each declaring
  `effects { Os.Syscall }` and, where it waits, `Thread.Block`. Linux first;
  a portable `pread`/`pwrite`/`fsync` backend, then `io_uring` behind the
  same rings.

Selection is static and per build: the root manifest's `replace` directive
(`83-modules.md` §4) maps the port's module path to one realization. Nothing
in the program text changes between a simulation build and a native one.
Two existing rules then do the rest: a package with `Sim` tests rejects
undeclared externs, so the native realization cannot be linked into a
simulation by mistake; and a hot path that declares `forbids { Os.Syscall }`
proves, over the specialized call graph, that it never reaches the
operating system (`60-effects-allocation.md` §2).

## 2. Shape: caller-owned completion rings

The port is io_uring-shaped because that is the shape a storage engine
wants (dbs RFC 0002 §12: batched submissions and completions, registered
files and buffers, linked write-then-fsync, bounded prefetch), and because
a synchronous call is the degenerate case of it. Everything is caller-owned
and bounded; `Memory.Allocate` never appears.

```oak
IoFile: type = struct { slot: u32 }                       // registered file, bounded table
IoBuffer: type = struct { base: u32, len: u32 }           // window into the registered region
IoRequest: type = struct {
  op: u32,        // 1 open, 2 close, 3 pread, 4 pwrite, 5 fsync, 6 fdatasync (7.. reserved: accept, recv, send)
  file: u32,      // IoFile.slot (open: the slot to fill)
  offset: u64,    // byte offset for pread/pwrite
  buf: IoBuffer,  // pread/pwrite window; open: the path bytes
  tag: u64,       // returned unchanged in the completion
  link: Bool      // this request must complete before the next submitted one starts
}
IoCompletion: type = struct { tag: u64, result: u32, error: u32 } // error 0 = ok, result = bytes
IoRing: type = struct { submitted: u32, completed: u32, files: u32 }

io_open_region: (ring: [*]IoRing, region: [*]u8, files: u32): ()
io_submit: (ring: [*]IoRing, requests: [*]IoRequest, request: IoRequest): Bool   // false when full
io_wait: (ring: [*]IoRing, requests: [*]IoRequest, completions: [*]IoCompletion, region: [*]u8, at_least: u32): u32
io_poll: (ring: [*]IoRing, requests: [*]IoRequest, completions: [*]IoCompletion, region: [*]u8): u32
```

- **Region.** One caller-owned byte region is registered with the ring;
  every buffer is a window `(base, len)` into it. This is the borrow rule
  made useful: views cannot be stored in requests (`50-borrowing.md`), so
  requests carry indexes into a region the caller passes to each call, and
  the native realization registers that region once (fixed buffers).
- **Files.** A bounded table of slots; `open` fills a slot, `close` frees
  it. The native realization registers the table's descriptors once.
- **Rings.** Submission and completion storage are caller-owned arrays of
  declared capacity; `io_submit` returns false when full, like
  `sim_schedule`. `io_wait` blocks until at least `at_least` completions
  are available (`Thread.Block`); `io_poll` never blocks.
- **Links.** A request with `link` set must complete before the next
  request submitted after it starts; a failure cancels the rest of the
  chain (their completions carry `Canceled`). `pwrite` linked to `fsync`
  is the durability idiom.
- **Errors.** A closed set carried in `IoCompletion.error`: `NotFound`,
  `Exists`, `Access`, `Busy`, `NoSpace`, `Invalid`, `Closed`, `TooLarge`,
  `Interrupted`, `Canceled`, `IoFailed`. The native realization maps errno
  onto it and records the raw code in the trace; no code becomes semantics
  the port did not name.

Synchronous helpers (`io_pread_sync`, `io_pwrite_sync`, `io_fsync_sync`)
are ordinary Oak over submit and wait, for programs that want the simple
shape; they inherit `Thread.Block` and `Os.Syscall` through the call graph.

## 3. Contract both realizations satisfy

- **Completion order.** Completions are unordered except along a link
  chain. A program that needs order links or waits.
- **Reads see writes.** Within one process, a `pread` submitted after a
  `pwrite`'s completion on the same file and range observes it, fsync or
  not.
- **Durability.** A completed `fsync` (or `fdatasync`) means every `pwrite`
  completed on that file before the fsync was submitted is durable across a
  crash, as far as the device is honest. The simulated device's lost-fsync
  fault exists precisely to test what a program does when it is not; the
  contract is stated against an honest device, and the ledger says when
  the device lied.
- **Crash.** Writes not covered by a completed fsync may vanish, in whole
  or as a prefix at block granularity (the torn write). A crash closes
  every file; restart reopens. The simulated realization is `sim_disk_crash`
  over the file table; the native one is the machine.
- **No hidden work.** No realization allocates, spawns, or retries on its
  own. A retry is a program decision with a new tag.

## 4. Simulated realization

Files are byte ranges over `SimDisk` blocks (one device per ring, a bounded
number of files with declared block ranges); `pwrite` packs bytes into words
and may tear at block boundaries exactly as the device does; `fsync`
persists; faults come from the tape through the device's mask; `io_wait`
completes ready requests in a tape-chosen order and after tape-chosen
delays (`SimSched` over pending requests as actors), and the crash and
restart events of `SimProcess` close and reopen the table. Every submit and
completion is a trace event with the request's tag, so the runner's replay
report names the operation that failed.

## 5. Native realization

Linux first. Increment one is the portable backend — `openat`, `close`,
`pread`, `pwrite`, `fsync`, `fdatasync` as extern bindings with
`effects { Os.Syscall }`, `io_wait` executing pending requests in order
(so links are trivially honored) and declaring `Thread.Block`. Increment
two is `io_uring` behind the same rings: registered files and the
registered region as fixed buffers, `IOSQE_IO_LINK` for links, batched
submission, `Direct IO` as an open flag for engines that own their cache.
macOS and other targets use the portable backend. The binding is the
trust boundary (`92-ffi.md` §2.3); the realization module carries an
audit list of its bindings.

## 6. What this is not

Not an asynchronous runtime: there are no coroutines or callbacks in the
port; resumption is the program's loop over completions (dbs RFC 0002 §13
keeps coroutines above IO). Not a socket API yet: the ring shape reserves
`accept`, `recv`, `send` as operations over the same region and tags, and
the simulated realization would route them through the event queue; that
is the second design. Not a file system: paths are opaque bytes handed to
`open`.

## 7. Questions for the owner before implementation

1. Module path and selection: is `replace io => ./io_sim` the right way to
   pick a realization, or should the manifest gain a `realize` directive so
   the choice is named for what it is?
2. One registered region or several: one keeps buffers as `(base, len)`
   indexes and matches io_uring's fixed buffers; several would need a
   region index in `IoBuffer`.
3. Whether the port should expose `open` at all, or whether the file table
   is filled at startup by the program's initialization phase (which
   `steady` in `oak.mod` would then keep the steady state away from).
4. Whether `fsync` should be split (`fdatasync` only) for the first slice
   of the database engine.

## 8. Order of work

1. This design, agreed.
2. `io/sim` in the testing module over the existing device, with the log
   store in the dbs repository ported from `sim_disk_*` to the port as the
   first consumer and the campaign that already runs there as its test.
3. `io/native` portable backend, differential-tested against `io/sim` on a
   fault-free run (same program, same tags, same completions modulo order).
4. `io_uring`.
