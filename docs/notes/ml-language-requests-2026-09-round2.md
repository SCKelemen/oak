# Note: the ml pilot's language requests, second list — assessment and plan

**Status: in progress, 2026-09-12.** Round one (F24, F1, F7, F4) is in flight. Baseline: `specification` after #237. Source:
the ml tensor-compiler pilot's second request list, in the order the
week's work raised them; the pilot's own numbering is kept (F7, F8, F24
are new; F1–F6 refer to the first list, `ml-language-requests-2026-09.md`).

| # | Request | What exists | Disposition |
| --- | --- | --- | --- |
| 1 | **F1** — a kernel form whose statement order is the emitted order; the slow matmul port was correct Metal with the loads after the multiplies | Kernels are Oak functions (`56-kernels.md`); the Metal emitter is a statement-by-statement translation | **Round one — landed.**  The emitter already preserves source order — every statement of a kernel body is emitted in place, expressions left to right, and hoisted lines (a cooperative reduction) go immediately before the statement that holds them. The chapter states it as a rule and a test pins it. What the C compiler or the Metal compiler reorders afterward is behind the language's memory model, not a change of meaning. |
| 2 | **F7** — realized-ness in the type, with the typestate handles | Typestate-indexed resources (`112-protocols.md` §5a), region records (`50-borrowing.md` §8c) | **Round one — landed.** The two did not compose: a record with a region parameter and a state parameter (`Node[R, S]` over `View[f32, R]`) is a typestate resource whose transitions return a record the region rule cannot place (`OAK-B0113`, "no single declared region"), because the per-state instantiation (`Node_Realized`) is not registered as a region record. Register instantiations of region records under their template's regions, and the pilot's `Lazy → Realized` protocol over tensor records types: an operand that must be in storage is a `Node[R, Realized]` parameter, and a wrong order is a type error rather than a boundary mark and a run-time trap. |
| 3 | **F6** — data layout as a type with field views: the `[q \| k \| v]` cache row is a record, `k` across positions a column view of a field | Proven-layout structs (`40-records.md`), views of record arrays, the strided `Tensor2` (`56-kernels.md` §8) | **Round two.** Two pieces: a **scalar view of a record view** — `scalars(rows)` reinterprets `[]Row` as `[]f32` when `Row` is a proven-layout struct whose fields are all one scalar type (contiguous by layout, so no padding and no reinterpretation of bits) — and `tensor_strided(data, rows, cols, row_stride, col_stride, offset)` in the tensor package, so `k` across positions is `tensor_strided(scalars(cache), positions, D, 3 * D, 1, D)`: a view, no stride arithmetic in an emitter, and the extraction models it (`Array Row → Array Float32` by the field order). |
| 4 | **F4** — effect-typed steps: three host round trips were legal Oak inside a captured step | Effect rows on function types (`60-effects-allocation.md` §2a), checked at arguments and declaration initializers | **Round one — landed.** The gap was the position: a step stored in a **record field** (`Step { run: f }`) and called through it (`s.run(ctx)`) is neither an argument nor a declaration, so the row was not checked and the call was unknown. Rows on record fields: the literal's field value is checked against the field's row, and a call through a rowed field contributes the row, so a host read inside a captured step fails the `forbids` that runs it. |
| 5 | **F2, F3** — a declared canonical order and reorder permissions; the fused attention introduced a second order beside the lane rule, both to be declarations Lean extracts | `reduce.tree` / `left` / `group_tree` with their Lean models; `laws { }` on operators (`10-syntax.md` §14a) | **Round two, documentation and one library form.** An order is a function: written in Oak, its extraction is its declaration, and a theorem relates it to another order (`tree_assoc`, `coop_eq_tree`). The online-softmax merge of fused attention is such a function; the chapter says so and gives the shape. What is new: `reduce.left` and `reduce.tree` over a window with a *state* (`fold_left_state`, the merge carrying `(max, sum)`), so the second order is a library call rather than a loop the pilot writes twice. |
| 6 | **F8** — text for emitters, or F1 which removes the emitters | `strings` builder, `float_format`, `uuid_format`, byte builder | **Round two, documentation first.** F1 removes the Metal emitter; the remaining emitters (other targets, diagnostics) have the pieces in `strings` and `float`. A recipe in the standard library README shows number-to-text into a caller-owned buffer; a gap found writing it becomes a library item. |
| 7 | **F24** — owners declared later in the file | Top-level owned arrays (`TABLE: [4]u32 = [...]`), borrowed with `view(&TABLE)` | **Round one — landed.** A function above the declaration failed with "view() argument must be &owner of an owned array": the borrow checker registers top-level owners as it walks statements, so a use above the declaration does not see it. Pre-register every top-level owner before the walk; functions already see later functions and types. |

## Order

2. F6 (`scalars`, `tensor_strided`), F5 (stateful folds and the chapter
