# Experimental X25519

`import("crypto/x25519")` provides the RFC 7748 Montgomery ladder over
`2^255 - 19`, implemented entirely in Oak. Go's `crypto/ecdh.X25519` is the
interoperability reference. This package is deterministic and does not obtain
entropy. It is not yet approved for production secret processing.

## API contract

| Function | Contract |
| --- | --- |
| `public_key(private_key: []u8, out: [*]u8): Bool` | Require exactly 32 input bytes and at least 32 output bytes. Compute X25519 with base point 9. |
| `shared(private_key: []u8, peer: []u8, out: [*]u8): Bool` | Require exactly 32 bytes for each input and at least 32 output bytes. Reject an all-zero shared secret. |

Both functions write exactly the first 32 output bytes on success, preserving
any suffix. Every failure leaves the entire output unchanged. Safe Oak callers
must supply disjoint borrowed inputs and exclusive writable output storage.
The caller must check the Bool result before using the output; old bytes in an
unchanged buffer are not a newly computed key.

Scalars are copied locally and clamped: clear the low three bits, clear bit
255, and set bit 254. Peer bit 255 is ignored. Noncanonical peer encodings
are accepted modulo the field prime, as required by RFC 7748; they are not
rejected merely for exceeding the prime. Canonical all-zero output is rejected,
including when a noncanonical or top-bit alias represents a low-order point.

Supply 32 bytes from a cryptographic entropy capability for a fresh private key.
Oak's simulation `random` package is not suitable. No key-generation API is
provided until the entropy capability and opaque secret owner are available.
The byte-view API and Bool errors are provisional. Secret copies and compiler
spills are not guaranteed erased.

## Composition with HKDF

After a successful `shared`, use `crypto/hkdf.key256` to derive application
keys from its 32-byte output. A protocol must specify the salt and unambiguous
`info` encoding, including protocol/version, roles, both ordered public keys,
and any additional authenticated transcript context. Use distinct labels for
directional keys. Raw DH output is not an application key. X25519 plus HKDF
does not authenticate the peer; signatures, a PSK, or another authenticated
protocol are necessary. The composition test uses an explicitly labeled,
fixed-width public-key transcript; it does not define a production protocol.

## Arithmetic design

Field elements are 17 little-endian radix-`2^15` limbs in `u64` storage.
Arithmetic helpers return bounded limbs, representing residues that may still
be at least the prime. Multiplication uses a 33-limb convolution and folds
upper limbs with `2^255 = 19 (mod p)`. Three fixed carry passes normalize the
limbs. Subtraction adds `2p` limbwise before subtracting. Encoding conditionally
subtracts `p` by adding 19 and selecting on the carry out of bit 254.

For bounded inputs, each convolution coefficient is at most
`17 * (32767)^2`; each folded coefficient is bounded by the conservative
`340 * (32767)^2 < 2^39`. Subtraction's smallest limbwise padding is 65498,
which exceeds any subtrahend limb. These are design bounds, not discharged
machine-arithmetic theorems. The representation avoids 128-bit multiplication
and target-specific assembly; it prioritizes a simple portable baseline.

The ladder has 255 iterations and mask-based swaps. Inversion uses the fixed
public exponent `p-2`. Branches and indices in field arithmetic depend on public
loop counters. The final success/failure branch discloses the all-zero rejection
result. This source structure is not a constant-time machine-code guarantee.

## Executable evidence

`compiler/e2e_crypto_x25519_test.go` checks:

- Both RFC 7748 section 5.2 scalar/u vectors; section 6.1 Alice/Bob public keys
  and shared secrets in both directions; one- and 1,000-iteration vectors.
  The million-iteration vector is not run.
- All seven individual public cases compiled through the host C backend, with
  one full scalar/u vector also executed by the Oak interpreter.
- 64 deterministic arbitrary scalar/peer cases against Go `crypto/ecdh`.
- Every noncanonical input from `p` through `2^255-1`, with both top-bit values;
  low-order representatives and top-bit aliases, including unchanged output
  on rejection.
- Private add/subtract/multiply helpers against independent Go `math/big`
  residues, including all-max limbs, modulus boundaries, carry chains,
  single-limb extremes and deterministic random inputs. Each result limb is
  checked below `2^15` before canonical comparison.
- Wrong input lengths, short output spans, suffix preservation, the public-key
  wrapper, bilateral agreement, and successful shared-secret-to-HKDF composition.

Run `go test ./compiler -run '^TestE2ECrypto' -count=1 -timeout 10m`.
The existing Crypto foundation workflow includes these tests automatically.
Go comparison code is test-only; Oak does not call Go for X25519 at runtime.

## Proof obligations: still open

| Layer | Obligation before a verified-production claim |
| --- | --- |
| Field refinement | Formalize radix decoding; prove convolution/folding congruence, no `u64` overflow, three-pass normalization, subtraction and canonical encoding for every bounded input. |
| Ladder | Prove the RFC ladder invariant, scalar decoding/clamping, field inversion including zero, and total behavior on curve/twist and noncanonical inputs. |
| API | Prove all failure paths preserve output, success preserves the suffix, all-zero rejection and safe storage contracts. |
| Key derivation | Refine SHA-256/HMAC/HKDF and the protocol's exact byte-level transcript encoding. |
| Protocol | Refine an authenticated protocol implementation into its Tamarin model, accounting for validation, entropy, compromise, persistence, and erasure assumptions. |
| ARM64 | Prove the implementation and linker/assembler preserve functionality through final executable bytes; establish leakage and secret-erasure contracts. |
| RV64 | Close the same functional, final-byte, leakage and erasure obligations independently. |

The existing `spec/tamarin/crypto/signed_dh.spthy` proves symbolic server
authentication, forward secrecy, and single acceptance under its documented
assumptions. Its hash abstracts transcript-bound derivation, not the HKDF
algorithm. `unauthenticated_dh.spthy` retains the expected attacker trace.
Neither model proves this X25519 arithmetic or its low-order rejection.
The models are rerun with `go run ./spec/tamarin/crypto -out <evidence-dir>`.
Public-vector success, host-C execution and symbolic proofs do not establish
ARM64 or RV64 correctness or timing properties. Wycheproof corpus integration,
opaque secret types, entropy capability, and implementation refinement remain
unfinished C1/C2 work.
